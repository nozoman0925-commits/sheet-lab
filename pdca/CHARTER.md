## 毎日の作業の割り当て

- 無料ツール: 1日3本まで。`site/tools/<slug>/{meta.json, body.html}`。ブラウザ内完結(外部送信なし)。純粋関数を `<script>` に置き、`site/verify/tools_test.js` に標準機能(Intl等)または独立した参照実装との照合テストを足し、全件合格してから公開。薄い量産は禁止(他と違う点、使い方、限界の明記が必要)。候補は `site/TOOLS_BACKLOG.md`。
- 早見表ページ: 計算で作れる表だけ(`site/verify/gen_tables.py` で生成し `tables_test.js` で照合)。外部データは出典URLを開いて確認した内容だけ。法律・金融・医療の断定、リアルタイム性が要る数値(税率改定など)は、確認日と出典を明記し、確認できなければ載せない。
- 商品(方針A): 1日1本まで。spec_ready の未作成が3件未満なら PRODUCTS.md の todo から仕様を補充(ローカルが1日4回作る)。税・法令の判断が必要な機能は含めない。LibreOfficeで再計算し、エラー0・主要ケースを検証してから、検証記録つきの商品説明を作る。販売(BOOTH)の口座開設と出品は人間。
- 公開時に TOOLS_BACKLOG / PRODUCTS の状態を更新し、LOGに記録する。数字が出たら伸びた系統に寄せる(7日分未満は判断しない)。
- 新商品が販売中になったら、その商品につながる記事か無料ツールを最低1つ作る。商品は PRODUCTS.md の selling 行に加え、site/products_meta.json(slug・できること・できないこと・タグ)を足すと /products/ に自動で載る。slug は PRODUCTS.md の `(slug: ...)` と同じにする。
- 週次レビューではページごとの検索表示とクリック(INBOX.mdの数字)を見て、伸びたテーマに寄せる。検索量の数字は推測で書かない。
- 外部SNSへの勝手な投稿、他サイトへのコメントやリンクの書き込み、不自然な被リンクづくりはしない。集客は検索・サイト内の導線(/products/、各ページの「関連」欄)・オーナーが行うX/noteで行う。

## 絶対ルール
1. 動かして確認したものだけを書く・公開する(数式、コード、主張)。出典は中身を確認したURLだけ。
2. 存在しない機能を販売しない。先行登録は、未提供と明記する。
3. 入力データの扱いは、実装で確認したことだけを表示する(例: 外部送信なし)。個人情報を取得しない。
4. 利益が出るまで有料施策(広告・有料ツール)を提案しない。ドメインは条件を満たしたらオーナーに判断を仰ぐ。
5. 規約違反の自動操作、偽レビュー、誇大表現、他者の文章・コードの流用をしない。
6. 契約・税務・法務・決済は、オーナーの確認が必要。必要に応じて専門家への確認を依頼する。
7. 数字は INBOX.md の実績か、出典つきの値だけ。推測は「仮定」と明記する。
8. できないことは、自動化可能/API確認が必要/人間操作が必要/代替手段あり のいずれかで明示する。

## クリック計測のルール
- **BOOTH商品へのリンクは、すべて `/go/<商品slug>/?from=<ページslug>` 経由にする**(記事・ツール・/products/・/about/ など、サイト内の全ページ)。BOOTHの商品URL(.../items/数字)を直接書かない。商品slugは site/products_meta.json の slug。/go/<slug>/ は build_site.py が自動生成する(noindex・サイトマップ非掲載・外部へデータを送るスクリプトなし)。ショップのトップ(https://nozoman.booth.pm/)へのリンクは直リンクでよい。
- 新しい商品を出品したら、products_meta.json に slug を追加する。
- 公開前に `grep -rn "booth.pm/items" site/content site/tool site/tools` が0件であることを確認する(build_site.py も dist 内の直リンクを警告する)。
- note用原稿のBOOTHリンクも `/go/<商品slug>/?from=note-<原稿名>` にする(例: https://sheet-lab-site.pages.dev/go/meibo-trial/?from=note-meibo-01)。
- 見方: Cloudflare Web Analytics の /go/ のページビュー = 商品へのクリック数、from = どの記事から。BOOTH側の閲覧数・購入はGoogleアナリティクス(BOOTHの測定ID欄)とBOOTH管理画面で見て、突き合わせる。

## Xの原稿(アカウント開設と投稿はオーナー、原稿はAI)
- 定期実行は、その日の最初の実行(0時台)で pdca/deliverables/outreach/x/<日付>.md に翌日分の投稿原稿を2本作る。サイトの検証済み記事・ツールから、数式と結果をそのまま使える形で書く(「LibreOfficeで計算」「Excelでは未確認」の別を守る)。
- **型を回す**: 各原稿に型を付ける(小技型 / よくある失敗型 / 数字型(検証結果の実数) / 逆説型 / 保存用のチェックリスト型)。同じ型を連続させない。
- **リンク**: 本文には原則リンクを入れない。リンクはプロフィールと固定ポスト(outreach/x/pinned.md)に置き、詳しく知りたい人には「プロフィールのリンクから」と書く。リンクつきは週に2本まで(必要ならリプライ欄に置く形で)。リンクは `?from=x`(固定ポストは `?from=x-pinned`)を付ける。
- **「経験・失敗」は実際の記録だけ**: 検証記録や LOG.md にある実際の失敗だけを使う。作り話は禁止。運営はAIが行っているとプロフィールに明記しているので、主語を偽らない(「検証したら」「試したら」は可。個人の職歴や体験の捏造は不可)。裏が取れないものは使わずオーナーに確認する(オーナー提供の例の「シフト表で浮動小数点の誤差によりNG→ROUNDで直した」「前株後株の式でスペースがあると想定と違う判定になった」は、2026-10-13時点でリポジトリ内に記録が見当たらないため未使用)。
- **型ごとの反応を記録**: pdca/deliverables/outreach/x/REACTIONS.md(列: 日付・型・書き出し・インプレッション・いいね・保存・プロフィールクリック)。オーナーが週に1回数字を伝えたら記入し、未記入は「未計測」。週次レビューで反応の良い型と書き出しを分析し、翌週に寄せる(数字が無いうちは推測で寄せない)。
- **需要の確認**: 新商品の仕様を書く前に、そのテーマの小技をXに出し、反応があったテーマを優先する。データがたまるまでは従来の優先順。
- **商品の告知**: 公開前・公開当日・公開後(使い方の切り口)で3回まで、毎回違う切り口で。商品の宣伝は週に2回まで。【PR】等、運営者の商品であることを明記し、BOOTHのリンクは `/go/<商品slug>/?from=x`(リンクつきの週2本の枠に数える)。
- 同じ文面やほぼ同じ投稿を繰り返さない。作る前に過去の原稿(outreach/x/)と比べる。
- 誇大表現・実績の捏造・「稼げる」系の言葉は禁止。ハッシュタグは1〜2個。
- AIは投稿・送信をしない(貼り付けはオーナー)。複数アカウントでの同種の投稿、架空の人物は禁止。

## 文体ルール(Xとnote)
- 話し言葉寄りの、やわらかいです・ます調。「〜ですよね」「〜ちゃう」「正直めんどくさい」などの口語も可。硬い言い回し(「〜である」「〜を確認した」「計算して確かめました」の連発、「LibreOfficeで計算」の毎回の付記)は避ける。検証の事実は「試したら」「6パターンで試したら」のように自然に入れる。
- 書き出しは読者の「あるある」や心の声から(例:「TRIMしたのに、スペースが消えない…」)。1文は短く、改行と空行でスマホで読みやすく。絵文字は1投稿2〜3個まで。
- 人間の体験の捏造は禁止(「先日うちの会社で」等は不可)。誇大表現・「稼げる」系も禁止。数式と結果は検証済みのものだけ。
- サイトの記事本文は検証の正確さを優先した丁寧な文体のままでよい。ただし導入文だけは読者の困りごとから入る。

## 出典に接続できないときの記事
外部サイトに接続できない実行環境では、Excel・スプレッドシートの関数や操作の記事に限り、LibreOfficeで実際に計算して確かめた結果を根拠に書いてよい。その場合は、sources に外部URLを書かず、本文と front matter に「出典: 筆者がLibreOfficeで計算して確認(検証スクリプト: site/verify/xxx.py)」と明記し、Excelとの差がありうる点(関数の有無、動的配列など)は「Excelでは未確認」と書く。税金・法令・労務・製品の仕様(新機能、サポート終了など)に関わる記事は、公式の出典を取得できたときだけ書く。

## 定期実行のLOG書式(進捗ページ /status/ が読む。2026-10-13追加)
- 定期実行は、作業の有無や上限到達にかかわらず、毎回かならず LOG.md の末尾に「## YYYY-MM-DD 定期実行(○時台JST)」の節を追記し、やったことを1行ずつ `- HH:MM [種類] やさしい短い文` の形で書く(HH:MM は日本時間)。
- 種類は 記事 / ツール / 商品 / note / X / 分析 / ルール のどれか。サイト公開以外(note原稿・X原稿・商品の仕様・分析・ルール変更)も、やったら必ず1行書く。何も作らなかった回も `- HH:MM [分析] 上限に達していたので、公開はなし` のように1行書く。
- 文は小学生にも分かる言葉で短く。専門用語を使うときはかっこで説明する。1日の上限に達した回は、文に「上限」と書く(ページが「きょうの記事はぜんぶ書いたので、つぎはあした」と表示する)。
- 従来の自由書式の節も、ページは読める(種類は文中の言葉から推測)。数字はページがファイルの実数から自動で入れるので、LOG に手で数を書かなくてよい。
