# 02 技術構成

## 1. 構成
```
[ブラウザ / スマホ（PWA）]
      │ HTTPS
[Webアプリ（Next.js + TypeScript）]
   ├─ 画面（React）
   ├─ API（Route Handlers / Server Actions）── 権限チェック①（ロール・案件メンバー・項目単位）
   ├─ 計算エンジン（packages/engine：画面とサーバーで同じコード）
   └─ PDF生成（サーバー側）
      │
[PostgreSQL] ── 行単位アクセス制御（RLS）＝権限チェック②
[ファイル保存（S3互換）] ── 署名付きURL・期限つき（案件メンバーのみ）
[バックアップ] ── 日次の自動取得＋別領域への複製、月1回の復元テスト
```
- **金額の計算はサーバーで確定する。** 画面でも同じエンジンで即時表示するが、保存時にサーバーが再計算し、画面から送られた金額は使わない。
- 権限は ①API と ②DB の二重。片方の実装漏れがあってももう片方で止まる。
- AI 拡張は「候補を返す外部モジュール」として API の外側に置く（03章 `ai_suggestions` は作らない。必要になった時点で追加）。

## 2. サーバー・DB の候補（**未決1**）
費用は変わるため、採用前に各社の公式料金ページで確認する。ここでは性質だけ比べる。

| 候補 | 中身 | 良い点 | 注意点 |
|---|---|---|---|
| **A. Supabase ＋ Vercel（推奨）** | PostgreSQL・認証・ファイル保存・RLS が一体 | 仕様書18章の推奨構成にそのまま合う。RLS で協力会社分離を DB で強制できる。データは標準の PostgreSQL なので他へ移せる | 無料枠は停止・容量などの制限があり、業務で常用するなら有料プランが前提になる見込み。データ保存場所（リージョン）を東京にする |
| B. Cloudflare（Workers＋D1＋R2） | SQLite 系 DB＋エッジ実行 | 安価になりやすい。既存サイトも Cloudflare Pages | D1 は PostgreSQL ではなく、RLS がない（権限はアプリ側だけになる）。仕様書の推奨と外れる |
| C. 国内クラウドの仮想サーバー＋PostgreSQL | 自前で全部持つ | 自由度が最大、国内保管 | 保守・バックアップ・セキュリティ更新を自社（または委託先）で持つ必要がある。仕様書21-9「特定の開発者しか保守できない構造にしない」に反しやすい |
| D. Firebase | NoSQL＋認証 | スマホ連携が強い | リレーショナルではないため、案件中心の集計・会計的な整合を取りにくい。仕様書18-1と外れる |

**推奨理由（A）**：①DB で協力会社を分離できる、②PostgreSQL なので「特定サービスに閉じ込めない」（仕様書14-3）、③認証・ファイル・DB を一社でまかなえ保守が軽い。
**進め方**：アカウント作成・支払い登録はご本人が行う。カード登録が必要な段階になったら作業を止めて報告する。

## 3. 技術スタック
| 領域 | 採用 | 理由 |
|---|---|---|
| 言語 | TypeScript | 金額・権限まわりの型の誤りをコンパイル時に止める |
| 画面 | Next.js（App Router）＋ React | 仕様書推奨。PWA 化しやすい |
| スタイル | Tailwind CSS ＋ 現行のデザイントークン | ダーク＋ブルーの見た目を移植 |
| DB アクセス | SQL マイグレーション（ファイルで管理）＋型生成 | スキーマ変更の履歴を Git に残す |
| 計算エンジン | `packages/engine`（依存なしの TypeScript） | 画面・API・テストで共通 |
| PDF | サーバー側で HTML → PDF（ヘッドレス Chromium） | 日本語フォントを埋め込み、端末差をなくす |
| テスト | 単体（engine・権限）＋ E2E（Playwright） | 08章 |
| 金額型 | 円の整数（bigint）。数量は小数3桁の numeric | 浮動小数を使わない |

## 4. リポジトリ構成（案）
```
apps/web/            Next.js（画面・API）
packages/engine/     計算エンジン（現行 js/engine.js を移植）
packages/checks/     送信前チェック・契約書19条チェック
packages/pdf/        書類テンプレート
db/migrations/       SQL（テーブル・RLS ポリシー）
db/seed/             開発用データ（本番には入れない）
docs/design/         本設計書
tests/e2e/           Playwright（権限の侵入テスト含む）
```
リポジトリを新しく作るか、sheet-lab の中に置くかも決める必要がある（sheet-lab は push すると main に自動マージされる設定のため、本番システムは**別リポジトリを推奨**）。

## 5. 環境
- 開発・検証・本番の3環境。本番データを開発に持ち込まない
- 秘密情報（DB 接続・API キー）はリポジトリに置かず、ホスティングの環境変数で管理
- 公開（デプロイ）はご承認を得てから行う
